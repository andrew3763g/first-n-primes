# Ревью: first_50_primes.py → first_50_primes_v2.0.py

Рецензент: Claude · 9 ноября 2026 · проверено на Python 3.10.12

## Итог

Версия 2.0 корректна: вывод по умолчанию побайтно совпадает с версией 1, `--self-test` проходит (≈2,5 с). Почти все рекомендации Codex выполнены правильно. Главные оставшиеся проблемы — не в алгоритме, а в обвязке:

1. Самотесты построены на `assert` и под `python -O` **молча «проходят»**, ничего не проверив.
2. CLI принимает `-n -5` и `-n 0` и печатает заголовок «First -5 prime numbers» без чисел, код возврата 0.
3. Имя файла `first_50_primes_v2.0.py` нельзя импортировать (`ModuleNotFoundError: No module named 'first_50_primes_v2'`), поэтому тесты невозможно вынести в отдельный модуль.
4. Внутренний цикл решета остался поэлементным циклом Python: замена на срезовое присваивание ускоряет решето в ~5 раз, решето только по нечётным — в ~10 раз (замеры ниже).

### Как проверял

- `diff` вывода v1 и v2.0 без аргументов — совпадают.
- `--self-test`, запуск под `-O`, CLI с `-n -5`, `-n 0`, `-n abc`, попытка импорта модуля.
- Бенчмарк решета v2.0 против двух альтернатив (срезовое присваивание; только нечётные) на L = 10⁵…10⁷, с проверкой равенства результатов.
- `tracemalloc` для `first_n_primes(10**6)`.
- Запас верхней границы `nth_prime_upper_bound` против истинного p_n для всех n = 6…10⁶.

### Подробности по пунктам с оговорками

**3. Docstring границы.** Написано, что запас +10 нужен, «чтобы начальное решето *usually* покрывало n простых». На самом деле для n ≥ 6 неравенство p_n < n(ln n + ln ln n) — доказанная теорема (Россер, 1938), поэтому граница покрывает n простых **всегда**, а запас +10 и цикл удвоения — чистая страховка от погрешности float. Codex назвал свою проверку «экспериментальной, не доказательством» — это корректно для его проверки, но в docstring лучше сослаться на теорему. Замер: минимальный относительный запас на n = 6…10⁶ — 6,2 %, ветка удвоения ни разу не срабатывает.

**6. Проверка типов.** Реализована правильно и единообразно. Оговорка: `isinstance(value, int)` отвергает `numpy.int64` и другие целочисленные типы с `__index__`. Для учебного скрипта это нормально; для библиотечного API идиоматичнее `operator.index(value)` с отдельным отказом для `bool`.

**8. `ValueError` в `nth_prime_upper_bound`.** Само по себе разумно, но теперь в модуле три разные политики для «пустого» входа: `first_n_primes(-1)` → `[]`, `sieve_of_eratosthenes(-1)` → `[]`, `nth_prime_upper_bound(0)` → `ValueError`. Функция используется только внутри, поэтому её стоит сделать приватной (`_nth_prime_upper_bound`), тогда расхождение перестанет быть частью публичного контракта.

**9. Самотесты.** Набор повторяет проверки Codex (−10…1000 для решета, −10…500 + 1000 для `first_n_primes`, 10 000-е простое = 104 729, принудительное расширение, типы). Проблемы:
- Всё на `assert`: под `python -O` проверки удаляются, и печатается «All self-tests passed.» — ложный зелёный результат.
- Принудительное расширение сделано подменой `globals()["nth_prime_upper_bound"]`. Это работает только потому, что `first_n_primes` ищет имя в глобалах при каждом вызове. Хрупко и непотокобезопасно.
- Тестовый код (≈100 строк из 230) живёт в боевом модуле.
- Не перенесены две проверки Codex из §4: достаточность границы для n = 1…10 000 и точное сравнение stdout CLI.

**10. CLI.** Codex писал «аргумент командной строки **с проверкой** целого количества». `type=int` проверяет только целость: `-n -5` и `-n 0` выводят заголовок без чисел и завершаются с кодом 0. Комментарий на стр. 218–219 («still reject negatives-as-empty politely…») это поведение описывает, но запутанно — на деле ничего не отвергается.

### Оценка сегментированного решета

**Вывод: не нужно сейчас; имеет смысл только для n ≳ 10⁷ или для бесконечного генератора.**

- **Память.** Сегментированное решето снижает память *решета* до O(√L) вместо O(L). Но, как показано выше, при «первых n простых» доминирует *результат* (36 байт на число против ~16 байт решета на число при n = 10⁶). Пока функция возвращает `list[int]`, сегментация уменьшит пик максимум на треть. Реальный выигрыш появляется только в паре с потоковым API (генератор, запись в файл).
- **Время.** В C/C++ сегментация выигрывает за счёт попадания сегмента в L1/L2-кэш. В Python со срезовым присваиванием накладные расходы на организацию сегментов (вычисление стартового смещения для каждого простого в каждом сегменте) съедают эту выгоду примерно до L ~ 10⁸. На масштабах задания — проигрыш.
- **Корректность и сложность.** Добавляет ~30 строк нетривиальной индексной арифметики и новые граничные случаи (стыки сегментов, квадрат простого на границе). Для учебного скрипта это ухудшает главное качество — прозрачность алгоритма.
- **Где он действительно хорош.** Как основа для `iter_primes()`: позволяет выдавать простые бесконечно без оценки верхней границы и без цикла удвоения, который в v2.0 пересчитывает решето с нуля.
